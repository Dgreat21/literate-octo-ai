# mastery — скиллы, плагины и реестр триггеров

Что агент умеет и **когда это включать**. Ядро — `registry.csv`: без него скиллы
это библиотека без каталога, о которой вспоминают постфактум.

## Структура

| Что | Где |
|---|---|
| Реестр с триггерами | `registry.csv` |
| Журнал применений скиллов (боевая метрика) | `usage_log.csv` |
| Отчёт по боевой метрике | `tools/skill_stats.py` |
| Таск-трекер | `tracker/` (tasks.csv + goals.csv) |

| Инфраструктура `.context` (ctx_lock.py) | `tools/` |
| Наши скиллы | `tools/addons/by_team/<имя>/SKILL.md` (формат Agent Skills) |
| Внешние библиотеки (референс, не редактируем) | `tools/addons/source/anthropics/{skills,plugins}/` |

## registry.csv

| Колонка | Что это |
|---|---|
| `ключ` | `MST-<id>`, автоинкремент, не переиспользуется |
| `имя` | имя скилла/плагина |
| `вид` | `skill` / `plugin` / `кандидат` (из журнала, не оформлен) / `прото-скилл` |
| `путь` | где лежит инструкция |
| `этапы` | статус-теги трекера через `;`: `анализ;планирование;разработка;тестирование;ревью;закрыт` или `любой` |
| `домены` | к каким направлениям относится, или `любой` |
| `триггер` | конкретная ситуация, в которой скилл включается |
| `статус` | `активен` / `кандидат` / `прото` / `deprecated` |

## Триггеры: как это работает

Этапы реестра — это **статус-теги трекера**: жизнь задачи и есть план,
по которому подбирается мастерство. Три типа срабатывания:

1. **Этапный.** Задача переходит в новый `статус_тег` → агент сверяется
   с реестром: что заявлено на этот этап в этом домене.
2. **Предметный.** В работе появился артефакт типа из триггера
   (.xlsx, MR на ревью, PDF, дашборд Superset) → включается соответствующая строка.
3. **Доменный.** Работа в домене → строки этого домена в приоритете.

Проверка одной командой (этап + домен):

```bash
python3 -c "
import csv
stage, domain = 'ревью', 'optimisation'
for r in csv.DictReader(open('mastery/registry.csv')):
    if (stage in r['этапы'] or r['этапы']=='любой') and (domain in r['домены'] or r['домены']=='любой'):
        print(r['ключ'], r['имя'], '->', r['путь'])
"
```

Правило для агента: **сработал триггер → прочитай инструкцию по `путь` до начала
работы**, а не в середине. Кандидаты (`вид=кандидат`) не инструкция, а напоминание
оформить: путь ведёт на запись журнала или прото-документ.

## Жизненный цикл скилла

```
work_journal.md («скилл: да») → registry.csv (вид=кандидат)
  → оформление через skill-creator (MST-5) → tools/addons/by_team/<имя>/SKILL.md
  → registry.csv (вид=skill, статус=активен) → строка в журнал
```

Прото-скиллы (доменные `RETRO_SKILLS.md`) мигрируют в `tools/addons/by_team/`
по одному тем же путём. Deprecated не удаляется из реестра — меняется `статус`.

## Боевая метрика (после оформления скилл живёт по ней)

Evals при создании отвечают «работает ли скилл в теории», боевая метрика —
«нужен ли он на практике». Механика:

1. Применил скилл → строка в `usage_log.csv` под локом:
   `дата,скилл(MST-ключ),кто,задача,исход,заметка`;
   исходы: `помог | частично | не_помог | вреден`.
2. `python3 mastery/tools/skill_stats.py` — отчёт: применения, за 30 дней,
   hit-rate (помог=1, частично=0.5), вердикт.
3. Вердикты: **боевой** (≥3 применений, hit-rate ≥70%) — кандидат на симлинк
   в витрину `skills/`; **на списание** (hit-rate <50% при ≥4 применениях,
   либо 0 применений за 42 дня) — предложение владельцу снять с витрины и
   сменить `статус`; **наблюдаем** — мало данных, работаем дальше.
4. `--selftest` у skill_stats.py — негативный контроль правил вердиктов
   (MST-15): правила обязаны «краснеть» на сломанном входе.

Подробнее — `.context/AGENTS.md` §4 «Боевая метрика скиллов».
