# Протокол лока и worktree

Все команды — из `.context/`. Владелец лока задаётся `CTX_AGENT` (id сессии).

```bash
cd .context && export CTX_AGENT=agent:<id-сессии>
```

## Когда лок обязателен

| Действие | Лок |
|---|---|
| Запись в `work_journal.md` | **обязателен** |
| Запись в `mastery/tracker/tasks.csv`, `goals.csv`, `links.csv` | **обязателен** |
| Запись в `mastery/registry.csv`, `usage_log.csv`, `mastery/plans/registry.csv` | **обязателен** |
| Правка любого общего файла основного дерева | **обязателен** |
| Чтение чего угодно | не нужен |
| Работа внутри своего worktree | не нужен |
| Файлы своего домена, которых никто не трогает | не нужен |

Лок держи **только на время записи**: захватил → прочитал → записал → отпустил.
Не держи лок, пока думаешь, читаешь другие файлы или ждёшь пользователя.

## Команды

```bash
python3 mastery/tools/ctx_lock.py acquire mastery/tracker/tasks.csv --wait 30
python3 mastery/tools/ctx_lock.py release mastery/tracker/tasks.csv
python3 mastery/tools/ctx_lock.py list      # кто что держит
python3 mastery/tools/ctx_lock.py clean     # снять протухшие
```

- Путь к цели — **относительно `.context/`**, всегда пиши его одинаково:
  `mastery/tracker/tasks.csv`, а не `./mastery/tracker/tasks.csv` и не абсолютный.
  Разные написания = разные локи = потеря взаимного исключения.
- `--wait N` — сколько секунд ждать. Без него acquire не ждёт вообще. Ставь
  `--wait 30` по умолчанию, `--wait 60` для журнала в конце промпта.
- `--ttl` — секунд до протухания, по умолчанию 1800 (30 мин). Не занижай.
- Код выхода: `0` — лок твой; `1` — BUSY или ошибка. **Проверяй код выхода**,
  а не глазами вывод: `... acquire X --wait 30 || exit 1`.

## Семантика BUSY

`BUSY` — не ошибка, а сигнал. Разрешено ровно два ответа:

1. **Подождать**: повторить acquire с бо́льшим `--wait`.
2. **Заняться другим**: взять следующий файл или другую подзадачу, вернуться позже.

Чужой живой лок **ломать нельзя**: не `rm -rf` каталога лока, не `release`
чужого лока, не обход записью мимо мьютекса. Если BUSY блокирует прогресс —
скажи об этом пользователю, а не «пробей» лок.

## TTL и перехват

`ctx_lock.py` перехватывает лок сам и только при **двух** условиях сразу:
TTL истёк **И** pid владельца мёртв. У CLI-локов pid умирает сразу после
команды, поэтому для них это фактически чистый TTL.

- Перехват печатается в stderr — не пропусти его в выводе.
- **Перехват — событие для `work_journal.md`.** Запиши: какой файл, кто был
  владельцем, сколько провисел.
- `clean` снимает все протухшие разом. Запускай его, когда `list` показывает
  `МЁРТВ`, а не «на всякий случай» в начале работы.

## Worktree

Несколько агентов одновременно → каждому своя ветка и своё дерево; в своём
дереве локи не нужны вовсе.

```bash
git -C .context worktree add ../.context_worktrees/<имя> -b wt/<имя>
# ... агент работает в .context_worktrees/<имя>/ без локов ...
git -C .context merge wt/<имя>
git -C .context worktree remove ../.context_worktrees/<имя>
```

- `work_journal.md` сливается сам: в `.gitattributes` стоит `merge=union` —
  append-only строки из веток объединяются без конфликта. Правило «одна строка
  в конце промпта» действует и в worktree.
- **`tracker/*.csv` в worktree опасен.** У них union-merge нет: две ветки
  правят одну строку задачи → честный git-конфликт, разрешать руками, и легко
  затереть чужое изменение статуса. Поэтому **статусы задач и любые правки
  трекера двигай в основном дереве под локом**, а не в worktree.
- То же и по той же причине — `registry.csv`, `mastery/plans/registry.csv`, `links.csv`.
- `mastery/.locks/`, `addons/source/`, `__pycache__/` в git не попадают.
- Merge делает **владелец worktree**, сразу после merge — `worktree remove`.
  Брошенное дерево = ветка, которую никто не сольёт.

## Типовой сценарий

Задача: добавить задачу в трекер и записать строку в журнал, рядом работает второй агент.

```bash
cd .context && export CTX_AGENT=agent:sess-7f3

# 1. осмотреться
python3 mastery/tools/ctx_lock.py list

# 2. захватить только то, что пишем
python3 mastery/tools/ctx_lock.py acquire mastery/tracker/tasks.csv --wait 30 || exit 1

# 3. ПРОЧИТАТЬ ФАЙЛ УЖЕ ПОД ЛОКОМ (id мог измениться, пока ждал) и записать
#    ... правка tasks.csv ...

# 4. отпустить сразу после записи
python3 mastery/tools/ctx_lock.py release mastery/tracker/tasks.csv

# 5. журнал — последним действием промпта, отдельным коротким локом
python3 mastery/tools/ctx_lock.py acquire work_journal.md --wait 60 || exit 1
#    ... дописать ровно одну строку в конец ...
python3 mastery/tools/ctx_lock.py release work_journal.md

# 6. закоммитить и убедиться, что за тобой не осталось локов
git -C . add -A && git -C . commit -m "..."
python3 mastery/tools/ctx_lock.py list
```

Ключевое в шаге 3: **читай файл после захвата лока, а не до**. Прочитанное
до ожидания BUSY уже устарело — сосед мог занять твой id или сменить статус.

## Анти-паттерны

- **Писать без лока «я быстро»** — конкурирующая запись теряется целиком.
- **Читать файл до acquire и писать по этому снимку** — затираешь чужую правку.
- **Держать лок весь промпт** — соседи получают BUSY на пустом месте.
- **Забыть release при ошибке/раннем выходе** — файл заперт на весь TTL.
  Отпускай в том же блоке, где захватил.
- **`rm -rf mastery/.locks/...`** руками — ломает чужой живой лок.
- **Разные написания пути** одного и того же файла — взаимное исключение молча исчезает.
- **Двигать статусы задач в worktree** — конфликт при merge, риск потери правки.
- **Оставить worktree непомерженным/неудалённым** — работа лежит в ветке, которой никто не видит.
- **Использовать один `CTX_AGENT` на двух сессиях** — в `list` не разобрать, кто держит.

## Чек-лист «снял ли я все локи»

- [ ] `ctx_lock.py list` — моего `CTX_AGENT` в выводе нет.
- [ ] На каждый мой `acquire` был `release` (в т.ч. на ветке с ошибкой).
- [ ] Если был перехват протухшего лока — записан в `work_journal.md`.
- [ ] Если был worktree — он смержен и удалён (`git -C .context worktree list` чист).
- [ ] Строка в `work_journal.md` дописана под локом, последним действием.
- [ ] Изменения `.context/` закоммичены в её локальный git.
