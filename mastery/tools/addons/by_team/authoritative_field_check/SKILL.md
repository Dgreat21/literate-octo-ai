Каждый проверяемый инвариант обязан читаться из авторитетного источника — того поля, где значение рождается, — а не из кэша, копии, денормализованного дубля или производного поля. Проверка по производному кэшу тавтологична: фикстура кормит кэш тем же значением, которое тест проверяет, и тест физически не может упасть. Скилл даёт признаки авторитетного поля, процедуру аудита существующих ассертов и следствие для версионирования и синка (производные поля не версионируются и не сравниваются).

# Проверка инварианта по авторитетному полю

## 1. Отличи авторитетное поле от производного

Задай четыре вопроса. Хватает одного «да» из правых столбцов, чтобы поле стало подозрительным.

| Вопрос | Авторитетное | Производное (кэш/копия) |
|---|---|---|
| Кто пишет значение? | пользователь, источник, бизнес-логика | пересчитывает сам движок при сохранении/рендере |
| Переживает ли пересборку? | да, восстановить неоткуда | пересобирается из других полей за один проход |
| Можно ли удалить без потери информации? | нет — информация исчезнет | **да — признак кэша** |
| Расходится ли между инстансами? | нет, значение одно | да: числовые id, пути, сгенерированные ключи |

Практика: **начни с третьего вопроса**. Удали поле мысленно и спроси, восстановится ли
оно из остального конфига. Восстановится — это кэш, и проверять по нему нельзя.

## 2. Почему проверка по кэшу опасна ИМЕННО в тестах

В проде расхождение кэша и авторитета обычно заметят. В тесте — нет, потому что
**фикстуру пишет тот же человек, что и ассерт**:

1. фикстура записывает в кэш значение `X`;
2. тест читает кэш и сверяет с `X`;
3. проверка сводится к `X == X` — тавтология.

Тест зелёный всегда. Он не упадёт, даже если сломать саму логику, ради которой написан:
логика авторитетного поля в проверке вообще не участвует. Это худший класс дефекта —
**тест не отсутствует, а создаёт ложную уверенность в покрытии**.

Практический признак тавтологии: сломай проверяемую логику намеренно (см. MST-15,
негативный контроль) — если тест остался зелёным, он читает кэш, а не авторитет.

## 3. Реальные примеры (superset_porcelain)

**Инвариант 3 — область видимости чарта.** Тест проверял область через производный кэш
`chartsInScope` при `scope = ROOT_ID` в фикстуре. Фикстура сама клала в кэш корневой
скоуп, тест его же и сверял — упасть тест не мог ни при какой поломке скоупинга.
Переведён на авторитетное `scope.rootPath`: путь пишет пользователь при настройке
фильтра, из кэша он не восстанавливается, и именно он определяет поведение.

**chartsInScope / tabsInScope.** Классический кэш по всем четырём признакам: пересчитывает
Superset, восстанавливается из `scope.rootPath` и структуры вкладок, удаляется без потери
информации — проверено живьём: **Superset принимает дашборд без этих ключей**. Исключены
из версионирования (`repo._drop_scope_cache`), предупреждение `validate` убрано.

**params.datasource и ключи chart_configuration.** `'<id>__table'` даёт 423 / 58 / 22 на
разных инстансах при одном и том же `dataset_uuid`; ключи `chart_configuration` —
числовые id чартов. Своё у каждого инстанса, лежит в конфиге как факт → даёт `pull`
на ровном месте. Тот же класс, что `chartsInScope`.

## 4. Процедура аудита существующих проверок

Не «просмотреть тесты», а механически по каждому ассерту:

1. **Выпиши источник значения.** Для каждого `assert` — из какого поля прочитано
   сравниваемое значение и по какому пути.
2. **Прогони поле по таблице §1.** Особенно вопрос «удалить без потери информации».
3. **Найди тавтологии**: значение в ассерте совпадает с тем, что положила фикстура,
   и авторитетное поле в цепочке чтения не участвует.
4. **Переведи на авторитетный путь.** Не «добавь ещё один ассерт» — замени источник,
   иначе тавтология остаётся и продолжает давать зелёный.
5. **Подтверди негативным контролем.** Сломай логику — новый тест обязан упасть.
   Не упал → перевод не состоялся.
6. **Проверь фикстуру на вырожденность.** `scope = ROOT_ID` — вырожденное значение,
   при котором «в области видимости» истинно для всех. Бери значение, при котором
   инвариант различает случаи.

## 5. Следствие для версионирования и синка

Тот же критерий работает за пределами тестов:

- **Производное поле не версионируется.** Оно восстанавливается из авторитетных полей,
  значит в снимке — избыточно.
- **Производное поле не сравнивается при синке.** Оно расходится между инстансами
  штатно (числовые id, пути), поэтому диффер показывает **ложные диффы «на ровном месте»**:
  `pull` там, где содержательно не изменилось ничего.
- **Ложные диффы обесценивают диффер.** Человек привыкает к шуму и перестаёт читать
  реальные изменения — дефект переезжает в прод через невнимательность.
- Решение: исключить производное поле из снимка явной функцией с говорящим именем
  (`_drop_scope_cache`), а не фильтром в диффере. Не сохранён — не разойдётся.
- Перед исключением **проверь живьём**, что потребитель принимает объект без поля.

## 6. Чек-лист

- [ ] Для каждого ассерта выписан источник значения (поле + путь).
- [ ] Каждое такое поле прогнано по четырём вопросам §1.
- [ ] Ни один ассерт не читает поле, которое удаляется без потери информации.
- [ ] Нет тавтологий «фикстура положила `X` → ассерт сверил `X`».
- [ ] Инвариант читается из поля, которое пишет пользователь/источник, а не движок.
- [ ] Фикстура не вырожденная: инвариант при ней различает истину и ложь.
- [ ] Негативный контроль пройден — на сломанной логике тест падает (MST-15).
- [ ] Производные поля исключены из версионирования и из сравнения при синке.
- [ ] Исключение проверено живьём: потребитель принимает объект без поля.
