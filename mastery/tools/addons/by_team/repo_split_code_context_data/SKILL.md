# Разделение на исполняемое / контекст / данные

Файл живёт там, где определена его **категория**, а не там, где его создали.

## 1. Три категории

| Категория | Определение | Где живёт (наш репозиторий) |
|---|---|---|
| **Исполняемое** | нужно, чтобы **программа работала**: код, тесты, стенд, точки входа | `dwh/`, репозиторий утилиты (`superset_porcelain/`) |
| **Контекст** | нужно, чтобы **человек или агент понял, где мы и почему**: планы, статусы, решения, отчёты, история | `.context/<домен>/` |
| **Данные** | **меняются без изменения кода**, могут отличаться по инстансам/средам | `dwh/.dashboards/`, отдельная папка данных |

Ориентир `.context/AGENTS.md` §10: **код → `dwh/`, эксперимент → `junk/`,
знание/контекст/решение → `.context/`.**

## 2. Тест принадлежности

Задай файлу три вопроса **в этом порядке**, первый «да» побеждает:

1. **Удали файл — программа перестанет работать или тест падёт?** → исполняемое.
2. **Содержимое отличается на prod/test/local или правится без правки кода?**
   → данные.
3. **Объясняет человеку/агенту, что происходит, что решили и что дальше?**
   → контекст.

Если «да» на 1 и 3 одновременно (README, AGENTS.md) — см. §3: побеждает
исполняемое, потому что файл описывает **код**, а не проект.

Контрольный признак контекста: **даты, статусы, имена людей, «почему отвергли
вариант Б»** — такое не должно ехать в дистрибутив.

## 3. Что осознанно остаётся при коде и почему

| Файл | Почему остаётся |
|---|---|
| `AGENTS.md` утилиты | **подхватывается агентским окружением автоматически из корня проекта**. Перенос в `.context/` сломал бы автоподгрузку инвариантов: агент их просто не прочитает. Это техническая зависимость, а не привычка |
| `README.md` пакета | руководство пользователя пакета — описывает код, едет вместе с ним в дистрибутив |
| `testing/README.md` | инструкция к стенду лежит **рядом со стендом**, иначе расходится с ним |
| тесты, фикстуры | часть исполняемого: удали — приёмка перестанет проходить |
| конфиги-**шаблоны** (`*.example`, дефолты в коде) | шаблон — часть кода; **заполненный** конфиг — данные |

Одной фразой: **при коде — что описывает код или требуется машиной; в контекст — что описывает проект.**

## 4. Секреты

Секреты не идут **никуда в git** — ни в код, ни в контекст, ни в данные.
В файле данных хранятся **только имена переменных окружения**, как в
`instance.json`: `{"url": "...", "password_env": "SUPERSET_PASSWORD"}` —
значение подставляется при запуске. Проверь `.gitignore` и `git log -p`
до переноса: `git mv` тащит секрет вместе с историей.

## 5. Процедура развязки существующей каши

1. **Инвентаризация.** Перечисли *все* файлы спорной папки (`ls -la`,
   `git ls-files`). Никаких «остальное по аналогии» — категория присваивается
   поимённо.
2. **Категоризация.** Прогони каждый файл через тест §2, запиши категорию
   и одной фразой причину. Спорные вынеси отдельно и реши явно (§3).
3. **Перенос через `git mv`** — сохраняет историю:
   `git mv <утилита>/ПЛАН.md .context/<домен>/PLAN.md` (реальный кейс: ПЛАН.md утилиты porcelain).
   Копирование + удаление историю рвёт. Если репозитории **разные** (у утилиты
   свой git) — переносится содержимое, старое место удаляется своим коммитом,
   а в журнале укажи, что история осталась в прежнем репозитории.
4. **Имена по конвенции принимающей стороны.** `ПЛАН.md` → `PLAN.md`
   (`.context/AGENTS.md` §3: `STATUS.md`, `PLAN.md`, `DECISIONS.md`).
   **Синонимы не плодим.**
5. **Обновить ссылки** — грепом по старому пути, не по памяти. Ломаются сразу
   в трёх местах: документы домена, код и скрипты (`bootstrap.py`, `reset.py`),
   инструменты `.context`.
6. **`check_refs.py`** — прогони, пока не станет чисто:
   `python3 .context/mastery/tools/check_refs.py`
7. **Переподтверди приёмку с новых путей.** Зелёные тесты «до» ничего не
   доказывают: перенос мог сломать чтение конфигов.
8. **Запиши границу в `README.md` домена** таблицей «где что лежит» и добавь
   строку в `work_journal.md`.

## 6. Реальный пример: superset_porcelain (2026-08-20)

Было: планы, отчёты, процесс для заказчика и конфиги дашбордов вперемешку
с кодом утилиты. Стало:

| Где | Категория | Что |
|---|---|---|
| `superset_porcelain/` | исполняемое | код, тесты, локальный стенд, `AGENTS.md`, `README.md` |
| `.context/porcelain/` | контекст | `STATUS.md`, `PLAN.md`, `ТЕСТИРОВАНИЕ.md`, `ПРОЦЕСС.md`, `СБОРКА.md`, `ПЕРЕИМЕНОВАНИЕ.md` |
| `dwh/.dashboards/` | данные | папка на инстанс (`prod`/`test`/`local`) → дашборд → `master` (как на инстансе) / `branch` (правки) |

Почему у данных именно такая раскладка: **один дашборд на разных инстансах —
разные конфиги** (Superset переставляет числовые id при импорте). Плоская
папка «все дашборды» склеила бы несовместимые версии. Результат:
`bootstrap.py`/`reset.py` перенацелены, приёмка переподтверждена с новых
путей (73 офлайн + 27 live).

## 7. Анти-паттерны

- **«Положу пока рядом с кодом, потом разнесу».** Не разнесёшь — вырастет каша.
- **Перенос `AGENTS.md` в контекст «для порядка».** Ломает автоподгрузку
  инвариантов, причём тихо: ошибки не будет, агент начнёт работать без правил.
- **Копирование вместо `git mv`.** История теряется (`git log --follow` пуст),
  два экземпляра гарантированно разъезжаются.
- **Данные внутри пакета кода.** Конфиг инстанса уедет в дистрибутив.
- **Секрет в файле данных «временно».** История git постоянна — ротация пароля
  становится обязательной.
- **Перенос без обновления ссылок и без повторной приёмки.**
- **Синонимы имён после переноса** (`ПЛАН.md` рядом с `PLAN.md`).

## 8. Чек-лист

- [ ] Файлы спорной папки перечислены поимённо, категория проставлена каждому;
      спорные (README, AGENTS.md, конфиги) решены явно, причина записана.
- [ ] `AGENTS.md` утилиты остался при коде (автоподгрузка не сломана).
- [ ] Перенос сделан `git mv`; для разных репозиториев — отмечено, где история.
- [ ] Имена приведены к конвенции принимающей стороны, синонимов нет.
- [ ] Секретов в перенесённых файлах нет — только имена переменных окружения.
- [ ] Ссылки обновлены в документах, коде/скриптах и инструментах `.context`;
      `check_refs.py` чист.
- [ ] Приёмка переподтверждена **с новых путей**.
- [ ] Граница описана таблицей в `README.md` домена, строка — в `work_journal.md`.
