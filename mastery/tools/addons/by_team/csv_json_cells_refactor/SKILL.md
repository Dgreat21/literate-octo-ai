# JSON в ячейке CSV: разносить на рёбра и прозу

Табличный реестр силён ровно тем, что он плоский: грепается, читается глазами,
даёт построчный дифф. JSON в ячейке отменяет все три свойства сразу.

## Симптомы — сработай, если видишь хоть один

1. **JSON/список внутри ячейки**: `[{"автор":"агент","текст":"…"}]`, `A;B;C`,
   вложенные объекты. Ячейка перестала быть скаляром.
2. **Дифф всей строки от мелкой правки**. Реальный замер трекера `.context`:
   добавление ОДНОЙ реплики переписывало строку задачи целиком, git показывал
   `1,14c1,14`. Ревью такого диффа невозможно: не видно, что именно изменилось.
3. **Двусторонняя связь = две записи**. `A блокирует B` в строке A и
   `B блокируется A` в строке B — одно ребро, записанное дважды. Рассинхрон
   здесь вопрос «когда», а не «если»: из 22 связей одна пара уже разъехалась
   (`DATACATALOG-4 → OPTIMISATION-1` без обратной) до всяких проверок.
4. **Правится только парсером**. Человек не может отредактировать поле в Excel
   или в редакторе, не сломав кавычки и экранирование.
5. **Словарь значений не соблюдается**: рядом с `блокирует` живут `после` и
   `связана` — внутри JSON никто не валидирует.

## Принципы разноса

- **Ребро = строка в отдельном CSV.** Схема `откуда,тип,куда`. Одно отношение —
  одна строка, ничего вокруг.
- **Храни ОДНУ активную форму, обратную выводи.** В файл пишется `блокирует`,
  `входит в`, `реализует`. Пассивной формы (`блокируется`) в данных нет — это то
  же ребро, прочитанное с другой стороны, и оно выводится при чтении
  (представлением/функцией). Так рассинхрон исчезает **как класс**, а не
  отлавливается проверками. Симметричные типы (`относится к`, `дублирует`)
  нормализуй по алфавиту ключей, чтобы форма записи была единственной.
- **Проза → markdown-файл на ключ.** `comments/<КЛЮЧ>.md`, секция на реплику.
  Файла нет = комментариев нет; пустых файлов не заводим. Проза остаётся прозой:
  её читают и правят руками, а дифф — `+4 строки` в своём файле.
- **Словарь типов нормализуй при переносе.** Значения вне словаря приводятся к
  словарным явно и записываются в отчёт миграции (`после` → `блокирует`,
  `связана` → `относится к`), а не тащатся дальше «как было».
- **Колонки-источники удаляй.** Пока старая колонка жива, она снова наполнится.
- **Формат остатка**: валидный CSV (RFC 4180, UTF-8), только плоские скаляры.

## Процедура миграции без потерь

1. **Зафиксируй базу**: коммит до миграции, чтобы сверять было с чем.
2. **Посчитай инварианты ДО**: число тикетов, число заполненных полей, число
   отношений, число реплик. Цифры выпиши — это критерий приёмки, а не ощущение.
3. **Распарси ячейки** одноразовым скриптом, разложи в `links.csv` и
   `comments/<КЛЮЧ>.md`.
4. **Схлопни дубли рёбер**: пара «прямая + обратная» → одно ребро в активной
   форме. Односторонние (разъехавшиеся) записи не теряй — они и есть находка.
5. **Проверь без потерь — тремя сверками**:
   - **посимвольная сверка полей**: все прочие поля тикетов совпали байт в байт
     (в кейсе — 273 поля, 21 тикет);
   - **пересчёт связей**: N исходных отношений выводятся из M рёбер
     (22 из 18 — разница ровно на схлопнутые пары, каждая объяснена);
   - **счёт реплик**: сколько было в JSON — столько доехало в markdown (12).
6. **Проверь дифф**: правка одной реплики = `+4 строки`, новая связь =
   `+1 строка`. Если снова переписывается вся строка — разнос не удался.
7. **Обнови документацию схемы** (README реестра) и правила: «никакого JSON в
   ячейках», «связь пишется один раз».

## Когда JSON в ячейке ДОПУСТИМ

Единственный случай: **истинно атомарный блоб**, который никогда не правится
частично и не участвует в связях — например, сырой ответ API, сохранённый как
улика, или конфиг, который читается и пишется целиком одной программой.
Признаки допустимости, нужны все сразу:

- внутрь блоба никто не смотрит запросом/грепом;
- никто не редактирует его руками;
- нет отношений «одно к многим» между блобом и другими строками;
- перезапись целиком — нормальный режим, и дифф всей ячейки никого не смущает.

Не выполнено хотя бы одно — разноси.

## Анти-паттерн «БД first, файл dump»

Соблазн лечить нечитаемый реестр переносом истины в БД, а файл держать
выгрузкой. Это не решение, а **вторая копия**: две копии реестра расходятся
всегда — не из-за плохих людей, а из-за первого же прогона, упавшего между
записью и дампом. Лечи причину (JSON в ячейке), а не симптом (неудобство
редактирования). Если БД нужна для запросов — направление синка строго
**файл → БД**, файл остаётся истиной, а производные формы (обе стороны связи)
в БД **выводятся представлением, а не хранятся**.

## Чек-лист

- [ ] В ячейках только плоские скаляры; JSON и списков нет.
- [ ] Отношения вынесены в отдельный CSV, схема `откуда,тип,куда`.
- [ ] Каждое ребро записано ровно один раз, в активной форме.
- [ ] Обратное направление выводится (представление/функция), не хранится.
- [ ] Симметричные типы нормализованы по алфавиту ключей.
- [ ] Типы связей — из словаря; значения вне словаря приведены и записаны.
- [ ] Проза — в markdown на ключ; нет файла = нет комментариев.
- [ ] Старые колонки-источники удалены из реестра.
- [ ] Сверки пройдены: поля посимвольно, N отношений из M рёбер, число реплик.
- [ ] Дифф проверен на живой правке: единицы строк, не весь файл.
- [ ] Второй копии реестра не заведено; синк только файл → БД.
- [ ] README реестра описывает новую схему; правило «без JSON» записано.
