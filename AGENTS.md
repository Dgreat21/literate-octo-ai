# AGENTS.md — правила работы с контекстной директорией

Эта директория (в рабочем workspace она называется `.context/` и лежит рядом
с кодом) — основная точка соприкосновения человека и агента: здесь живут
рабочий контекст, планы, решения и журнал. Кода здесь нет — код живёт в своём
репозитории, прототипы в песочнице. Единственное исключение — `mastery/tools/`
и `tools/` внутри доменов: инфраструктурные скрипты для самой директории.

Правила ниже обязательны для любого агента, работающего в этом репозитории.
При противоречии с `AGENTS.md` кодового репозитория — тот главнее для кода,
этот файл главнее для контекста.

---

## 1. Карта директории

```
.context/
├── AGENTS.md          # этот файл
├── work_journal.md    # журнал действий — САМЫЙ ВАЖНЫЙ ФАЙЛ, append-only
├── rules/             # устав: rule-<id>.md — нерушимые принципы (§11)
├── design_docs/       # ВИТРИНА: README + симлинки на опубликованные диздоки (§6)
├── skills/            # ВИТРИНА: README + симлинки на частые скиллы (§4)
├── mastery/           # мастерская — всё, чем координируется работа (см. §4):
│   ├── registry.csv   #   реестр скиллов/плагинов с триггерами
│   ├── tracker/       #   таск-трекер: tasks.csv + goals.csv (§5)
│   ├── plans/         #   реестр планов (§7)
│   ├── design_docs/   #   КУХНЯ диздоков: черновики и принятые (§6)
│   ├── team/          #   как мы работаем: план этапа, статус, риски, треки, решения
│   ├── tools/         #   инфраструктура: ctx_lock.py, check_refs.py; tools/addons/ — скиллы и плагины
│   └── .locks/        #   мьютексы (вне git)
├── .other/            # то, для чего пока рано заводить домен
└── <домен>/           # направление деятельности, по папке на направление
```

Витрины — физические папки в корне с README и набором симлинков: наружу
показывается только то, что осознанно выложено; истина остаётся в мастерской.

Смысловая граница: **домены — над чем работаем** (предмет), **мастерская — как
работаем** (координация и инструменты). Поэтому `team/` живёт в мастерской.

### Домены сейчас

| Домен | Про что | Точка входа |
|---|---|---|
| `example-domain/` | Шаблон-образец: как выглядит домен изнутри | `example-domain/README.md` |
| `agent-infra/` | Стек Herdr + dsh: сборка, headless-обёртка, Telegram-бот, удалёнка (трекер: `INFRA-*`) | `agent-infra/README.md` |

Список в этой таблице поддерживается актуальным: завёл или задепрекейтил домен —
обнови таблицу тем же коммитом.

## 2. `work_journal.md` — журнал действий

Самый важный файл директории. История того, что просили и что было сделано.

### Формат

Markdown-таблица, одна строка = один промпт:

```markdown
| 2026-08-20 00:49 | что просили | что сделал | скилл: нет |
```

Колонки: **время** (`YYYY-MM-DD HH:MM`, локальное) · **что просили** (суть запроса
в одну фразу) · **что сделал** (см. градацию ниже) · **скилл** (`нет` / `да: <что
именно стоит оформить>` — кандидат в `mastery/`).

### Правила ведения

1. **В конце каждого промпта агент добавляет ровно одну строку.** Это не опционально.
2. **Файл append-only.** Никому нельзя удалять файл, переписывать или убирать из него
   какой-либо контент. Опечатка в старой записи исправляется новой записью, а не правкой.
3. **Гранулярность — здравый смысл, а не каждый пук.** Правильный уровень:
   «файл создан», «файл отредактирован», «направление создано», «домен помечен
   deprecated», «выкат волны 1 на прод». Неправильный: перечисление каждого
   прочитанного файла и каждой запущенной команды.
4. Пишем по-русски, имена файлов — как есть.

### Пример

```markdown
| 2026-08-20 00:15 | составить план работ по Ганту | созданы team/{STATUS,PLAN,RISKS,TRACK_*,DECISIONS,README}.md | скилл: да — разбор xlsx-Ганта парсером |
| 2026-08-20 00:49 | AGENTS.md для .context | создан .context/AGENTS.md, заведены skills/ и .other/, папка other удалена | скилл: нет |
```

## 3. Домены (направления деятельности)

Домен = папка в корне контекстной директории = отдельное направление работы.

### Стандарт домена

- **`README.md` обязателен** — что это за направление, какие файлы есть и когда
  какой читать (см. `example-domain/README.md` как образец). Остальные файлы —
  по необходимости.
- Устоявшиеся имена файлов, если они нужны домену: `STATUS.md` (где мы),
  `PLAN.md` (что дальше), `DECISIONS.md` (журнал решений), `RISKS.md`,
  `INVENTORY.md` (измеренные факты). Не плоди синонимы — если файл про статус,
  он называется `STATUS.md`.
- Тяжёлые генерируемые артефакты — в подпапку `generated/` внутри домена.

### Создание домена

Создавай, когда у направления появляется устойчивый контекст (больше пары файлов
или больше пары недель жизни). До того — держи в `.other/`. Создание домена —
событие для `work_journal.md` и для таблицы в §1.

### Deprecation

Домен не удаляется — помечается: к имени папки добавляется префикс `deprecated_`:

```
example-domain/  →  deprecated_example-domain/
```

Содержимое не трогается. Пометка — событие для `work_journal.md` и таблицы §1.

## 4. `mastery/` — скиллы, плагины и реестр триггеров

Скилл — переиспользуемая инструкция «как делать» (не «что сделано» — это журнал,
и не «что решили» — это `DECISIONS.md` домена). Подробности — `mastery/README.md`.

Структура:

- **`mastery/registry.csv`** — реестр с триггерами: какой скилл/плагин на каком
  этапе и в каком домене включается. Ключ `MST-<id>`, автоинкремент.
- **Наши скиллы** — `mastery/tools/addons/by_team/<имя>/SKILL.md` (snake_case),
  по формату Agent Skills (спека и шаблон —
  `mastery/tools/addons/source/anthropics/skills/{spec,template}/`).
- **`mastery/tools/addons/source/`** — внешние библиотеки как референс (клоны
  `anthropics/skills`, `anthropics/plugins`). Не редактируем, в git не входят.
- **Витрина `skills/` в корне** — README + симлинки на часто необходимые скиллы
  для быстрого доступа. Истина — реестр; витрина — кэш для руки: симлинк
  добавляется, когда скилл зачастил, убирается, когда перестал (событие журнала).

### Триггеры — правило для агента

Этапы реестра = статус-теги трекера. Агент сверяется с `registry.csv`:

1. **при переводе задачи в новый `статус_тег`** — что заявлено на этот этап
   в этом домене;
2. **при появлении артефакта** из предметного триггера (.xlsx, MR, PDF, дашборд);
3. сработало → **читает инструкцию по `путь` до начала работы**, не в середине.

Жизненный цикл: журнал («скилл: да») → registry (`кандидат`) → оформление
(skill-creator) → `by_team/` → registry (`активен`) → строка в журнал.
Прото-скиллы из доменных `RETRO_SKILLS.md` мигрируют этим же путём.

### Наши скиллы `by_team/` — можно и нужно использовать

В `by_team/` лежат оформленные командные скиллы. Они не музей: при срабатывании
триггера из `registry.csv` агент **обязан** прочитать SKILL.md до начала работы
и работать по нему. Краткая карта «когда что»:

| Когда | Скилл |
|---|---|
| написал проверку/тест/гейт и хочешь сказать «зелёно» | `verifier_negative_control` |
| пишешь/ревьюишь тест — откуда берётся проверяемое значение | `authoritative_field_check` |
| хеш/контрольная сумма по колонкам в PG/GP | `hash_function_choice` |
| анализ планов запросов, детекторы анти-паттернов | `plan_tags_explain_json` |
| запись в общие файлы контекста, параллельные агенты | `lock_worktree_protocol` |
| запись в существующий домен после долгого черновика | `domain_state_check` |
| .xlsx без openpyxl (Гант, выгрузки, отчёты) | `xlsx_stdlib_parse` |
| CSV → Postgres без драйверов | `csv_to_postgres_copy` |
| JSON/связи в ячейках CSV-реестра, нечитаемые диффы | `csv_json_cells_refactor` |
| «где должен жить этот файл»: код/контекст/данные | `repo_split_code_context_data` |
| часть системы не продана / чужой контур | `enrichment_slots` |
| крупный необратимый выбор перед `DECISIONS.md` | `llm_council` |
| mermaid-диаграмма: граф задач, канбан, sankey, поток | `mermaid_from_data` |
| языковая копия BI-дашборда | `dashboard_i18n_copy` |

### Боевая метрика скиллов

Скиллы оцениваются не только evals при создании, но и по факту применения:

- **`mastery/usage_log.csv`** — журнал применений: после каждого применения
  скилла агент добавляет строку `дата,скилл(MST-ключ),кто,задача,исход,заметка`.
  Словарь исходов: `помог | частично | не_помог | вреден`. Это не опционально:
  без строки в usage_log применение считается не случившимся, и скилл честно
  уедет «на списание». Файл общий — писать под локом (`ctx_lock.py`).
- **`mastery/tools/skill_stats.py`** — отчёт: применения, hit-rate
  (помог=1, частично=0.5), вердикты. Правила: «боевой» ≥3 применений и
  hit-rate ≥70%; «на списание» — hit-rate <50% при ≥4 применениях либо
  0 применений за 42 дня. `--selftest` — негативный контроль самих правил.
- «На списание» — предложение агента, решение за владельцем: симлинк снимается
  с витрины, статус в registry меняется, файл скилла не удаляется.
- Пересматривать отчёт — при закрытии крупной задачи или раз в пару недель;
  вердикт «на списание» — событие для `work_journal.md`.

## 5. `mastery/tracker/` — задачи и цели

Текстовый таск-трекер: `mastery/tracker/tasks.csv` (задачи)
и `mastery/tracker/goals.csv` (цели → проекты → вехи). Полная схема,
словарь статусов и правила — `mastery/tracker/README.md`. Инструмент
(UI + ядро записи) выделен в отдельный пакет — сабмодуль
`mastery/tools/saturday-tracker/`.

Главное:

- **Единственный источник истины.** Копий трекера по доменам нет: срез по
  направлению даёт ключ-префикс (`<ДОМЕН>-*`).
- **Ключ** — `<НАПРАВЛЕНИЕ>-<id>`, направление капсом = домен, id автоинкремент,
  не переиспользуется.
- **Когда писать:** не каждый промпт, а когда есть понятная выполнимая атомарная
  задача. Черновики и мысли — в домен.
- Строки редактируются (это не журнал), но `обновлено` меняется, а история
  обсуждения копится в `comments/<КЛЮЧ>.md`, не затиранием.
- Связи — отдельным файлом `links.csv`, ребро пишется **один раз**
  (обратная сторона выводится при чтении). Подробности — README трекера.
- Задача заведена или сменила статус — это событие для `work_journal.md`.

### Трекер как канал общения с владельцем

У трекера есть локальный UI (`python3 -m saturday_tracker`,
`http://127.0.0.1:8777`), и он открывает карточку по прямой ссылке:

```
http://127.0.0.1:8777/t/DEMO-2
```

**Это меняет способ отвечать.** Вместо пересказа «завёл задачу, она в ревью,
вот её DoD» — кидай ссылку: человек откроет и увидит всё сам, вместе с
описанием, DoD, связями и обсуждением. Пересказ в чате устаревает при
следующей же правке, ссылка — нет.

Что из этого следует:

1. **Кидай ссылку всегда, когда упоминаешь тикет в ответе.** Полным URL,
   а не голым ключом: по ключу надо идти искать, по ссылке — один клик.
2. **Веди трекер активно, не спрашивая разрешения.** Появилась понятная
   атомарная задача — заводи в беклог сразу. Порог прежний (см. «когда
   писать» выше): задача, а не мысль. Мысль — в домен.
3. **Комментируй ход работы в самом тикете.** Что выяснилось, где
   споткнулся, почему выбран этот путь — принадлежит тикету, а не только
   чату. Чат прокручивается, `comments/<КЛЮЧ>.md` остаётся и лежит в git.
4. **Двигай статусы по факту, а не в конце.** Взял в работу —
   `разработка`, отдал на просмотр — `ревью`. Смена статус-тега включает
   триггеры `mastery/registry.csv` (§4), и читать их надо ДО работы.
5. **Закрывая задачу, заполняй `резолюция_тег` и `резолюция`.** Пост-мортем
   в одну-две строки: что вышло, что поняли. Без него закрытая задача через
   месяц неотличима от заброшенной.

Писать — через UI или ядро записи пакета трекера: оба идут одним путём (лок
`ctx_lock`, атомарная запись, git-коммит на правку). Правка CSV руками
тоже допустима, но лок тогда берёшь сам (§8).

## 6. Диздоки: кухня `mastery/design_docs/` и витрина `design_docs/`

Диздок — самодостаточный документ уровня «прочитал — понял проблему, решение,
этапы, риски и что подписать», предъявляемый заказчику/команде. По файлу на
диздок: `mastery/design_docs/<домен_или_тема>.md`.

**Draft/published — это кухня/витрина.** Все диздоки живут на кухне.
Опубликованный диздок — тот, на который владелец (не агент) положил симлинк
в корневую витрину `design_docs/`:

```bash
cd design_docs && ln -s ../mastery/design_docs/<имя>.md <имя>.md
```

Снятие с публикации — удаление симлинка; файл на кухне не трогается.
Публикация и снятие — события для `work_journal.md`. Битые симлинки
(диздок переименовали) ловит `check_refs.py`. Правило rule-9.

- Шапка обязательна: версия, автор, дата, дедлайн ревью, ссылка на задачу
  в `tracker/`.
- Диздок **синтезирует** доменные файлы (`INVENTORY`/`PLAN`/`DECISIONS`), а не
  заменяет их: детали живут в домене, диздок ссылается. Правило одного источника:
  цифра рождается в домене, диздок её цитирует.
- Принятый диздок не переписывается под новую реальность — выпускается новая
  версия (версионирование в шапке); история решений остаётся читаемой.

## 7. `mastery/plans/` — реестр планов

План — пошаговый документ, по которому исполняется работа: этапы, шаги, гейты
(не путать с диздоком — «что и почему строим» — и со `STATUS.md` — «где мы»).
Правила — `mastery/plans/README.md`.

- **Каждый живой план зарегистрирован** в `mastery/plans/registry.csv`
  (ключ `PLAN-<id>`). Незарегистрированный план — черновик, ссылаться на него
  как на план работ нельзя.
- Доменные `PLAN.md` остаются в доменах, реестр ссылается на них колонкой `файл`.
  Новые планы, не выросшие из одного домена, — `mastery/plans/PLAN-<id>_<slug>.md`.
- Исполняемый план привязан к задаче трекера; его этапы соотносятся
  со статус-тегами — по ним срабатывают триггеры `mastery/registry.csv`.
- Статусы: `черновик` → `утверждён, ждёт исполнения` → `выполняется` →
  `выполнен` / `устарел`. Устаревшее помечается, не удаляется.

## 8. Параллельная работа: локальный git, мьютексы, worktree

Контекстная директория — **собственный git-репозиторий**, отдельный от кодового:
родительский репозиторий его не видит (`.gitignore` + `.git/info/exclude`).
История контекста — это git-история; осмысленная пачка изменений = коммит.

### Мьютексы на файлы

Пока работаешь с общим файлом — держи лок. Инструмент: `mastery/tools/ctx_lock.py`
(атомарный `mkdir` в `.locks/`, метаданные владельца в `owner.json`):

```bash
python3 mastery/tools/ctx_lock.py acquire mastery/tracker/tasks.csv --wait 30  # захват
python3 mastery/tools/ctx_lock.py release mastery/tracker/tasks.csv            # отпустить
python3 mastery/tools/ctx_lock.py list                                         # кто что держит
python3 mastery/tools/ctx_lock.py clean                                        # снять протухшие
```

- **Обязательно** для записи в `work_journal.md`, `tracker/*.csv` и любые общие
  файлы основного дерева. Чтение лока не требует.
- Владельца задаёт `--owner` или переменная `CTX_AGENT` (для агентов — id сессии).
- Протухание: лок перехватывается, только если TTL (30 мин) истёк **и** pid
  владельца мёртв. У CLI-локов pid умирает сразу после команды, поэтому для них
  это фактически чистый TTL. Перехват — событие для `work_journal.md`.
- `BUSY` — это не ошибка, а сигнал подождать или заняться другим файлом.
  Ломать чужой живой лок нельзя.

### Worktree для параллельных агентов

Несколько агентов одновременно → каждому своя ветка и своё дерево, мьютексы
нужны только в основном дереве:

```bash
git worktree add ../.context_worktrees/<имя> -b wt/<имя>
# ... агент работает в .context_worktrees/<имя>/ без локов ...
git merge wt/<имя> && git worktree remove ../.context_worktrees/<имя>
```

- `work_journal.md` сливается автоматически: в `.gitattributes` стоит
  `merge=union` — append-only строки из веток объединяются. Правило «одна строка
  в конце промпта» действует и в worktree.
- `tracker/*.csv` union-merge **не имеет**: правки одной строки из двух веток —
  честный конфликт, разрешается руками. Поэтому статусы задач лучше двигать
  в основном дереве под локом.
- `mastery/.locks/`, `mastery/tools/addons/source/`, `__pycache__/` в git
  не попадают (`.gitignore`).

## 9. `.other/` — преддоменное хранилище

Для того, чему пока рано заводить домен.

- **Вложенность минимум один уровень**: не файлы россыпью в `.other/`,
  а `.other/<тема>/<файлы>`.
- В каждой тематической папке — `project.md`: что это, зачем, статус.
- Тема выросла → повышается до домена (переносится в корень контекста,
  `project.md` становится `README.md`). Это событие для журнала.

---

## 10. Подключённые проектные папки (вне контекста)

В рабочем workspace рядом с контекстной директорией живут:

| Путь | Что это | Правила |
|---|---|---|
| `<код>/` | Основной кодовый репозиторий проекта | его корневой `AGENTS.md` — конвенции разработки обязательны |
| `junk/` | Песочница: прототипы и одноразовые скрипты | правил нет; ничто отсюда не попадает в прод, не пройдя конвенции кода |
| `<утилита>/` | Выделенные утилиты — отдельные git-репозитории внутри workspace | у каждой свой `AGENTS.md`; контекст по ней — в её домене |

Ориентир, куда что класть: **код** → кодовый репозиторий, **эксперимент** →
`junk/`, **знание/контекст/решение** → контекстная директория.

## 11. `rules/` — устав

Нерушимые принципы работы, по файлу на правило: `rules/rule-<id>.md`,
индекс — `rules/README.md`. Разделение ответственности: **устав говорит
«что нерушимо», AGENTS.md — «как именно»**; механика меняется, принципы
переживают реорганизации.

- Правило вводится, меняется и помечается устаревшим **только явным решением
  владельца** (rule-10). Агент предлагает — владелец вводит.
- id автоинкремент, не переиспользуется; устаревшее помечается, не удаляется.
- Новое правило = файл + строка в индексе + запись в журнал.
